# T1059.001 – Encoded PowerShell command

| Field | Value |
|---|---|
| MITRE ATT&CK | [T1059.001 – PowerShell](https://attack.mitre.org/techniques/T1059/001/) |
| Wazuh rule | 100100 (level 12) |
| Log source | Sysmon Event ID 1 – Process creation |
| Status | ⬜ Not tested yet |

## What the attacker does
Attackers often Base64-encode PowerShell commands (`-EncodedCommand`) so that the real payload isn't visible in plain text on the command line, and so that simple keyword filters miss it. Malicious macros and droppers use this all the time.

## How I simulated it
```powershell
$b64 = [Convert]::ToBase64String([Text.Encoding]::Unicode.GetBytes("Write-Host 'T1059.001 lab test'"))
powershell.exe -NoProfile -EncodedCommand $b64
```
The encoded command only prints a message.

## The detection logic
The rule fires when a Sysmon process-creation event has:
- `image` ending in `powershell.exe` or `pwsh.exe`, **and**
- a command line with any abbreviation of `-EncodedCommand` (`-e`, `-enc`, `-ec`, …) followed by a Base64 string of 20+ characters.

Matching every abbreviation matters because PowerShell accepts any unique prefix of a parameter name, and attackers use `-e` or `-enc` to evade detections that only look for the full word.

## False positives and tuning
Some legitimate management tools (SCCM, some installers) also use encoded commands. In a real environment I would:
- exclude known parent processes (for example `CcmExec.exe`) after reviewing them, and
- raise the severity when the parent is an Office application (`winword.exe`, `excel.exe`).
