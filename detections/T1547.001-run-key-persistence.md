# T1547.001 – Run key persistence pointing to a user-writable folder

| Field | Value |
|---|---|
| MITRE ATT&CK | [T1547.001 – Boot or Logon Autostart Execution: Registry Run Keys](https://attack.mitre.org/techniques/T1547/001/) |
| Wazuh rule | 100109 (level 12), child of built-in 92300 |
| Log source | Sysmon Event ID 13 – Registry value set |
| Status | ✅ Detected |

## What the attacker does
Malware adds a value under `...\CurrentVersion\Run` so that it starts again every time the user logs in. It is one of the most common persistence methods because it needs no admin rights when written to `HKCU`. The payload usually sits somewhere any user can write to: `C:\Users\Public`, `%AppData%`, `%Temp%` or `C:\ProgramData`.

## How I simulated it
```powershell
$key = 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Run'
New-ItemProperty -Path $key -Name 'LabTest' -Value 'C:\Users\Public\labtest.exe' -PropertyType String -Force
Start-Sleep -Seconds 5
Remove-ItemProperty -Path $key -Name 'LabTest' -Force
```
The value points to a file that does not exist and is deleted after 5 seconds.

## What the logs showed
Sysmon Event ID 13 recorded `TargetObject = HKU\<SID>\Software\Microsoft\Windows\CurrentVersion\Run\LabTest` and `Details = C:\Users\Public\labtest.exe`, set by `powershell.exe`.

Wazuh already has rule **92300** for Run key changes, but it is **level 0**: it matches the event and records nothing. Every software updater writes Run keys, so alerting on all of them would be noise.

## The detection logic
Rule 100109 is a **child of 92300** (`<if_sid>92300</if_sid>`), so it only looks at events Wazuh already recognised as Run key changes. It raises a level-12 alert when the new value (`win.eventdata.details`) points into a user-writable location: `Users\Public`, `AppData`, `Temp` or `ProgramData`.

Implementation detail: Wazuh's eventchannel decoder escapes backslashes, so the field contains `C:\\Users\\Public\\...`. The regex uses `\\+` to match one or more backslashes, so it works whichever way the value is stored.

## Result
✅ Rule 100109 fired at level 12 about 2 seconds after the value was written (test run 2, 4 Oct 2026).

## False positives and tuning
Some legitimate apps install per-user into `%AppData%` or `%LocalAppData%` and register a Run key there (chat apps, cloud-sync clients, updaters). In a real environment I would:
- review what fires during the first week and allow-list known-good paths and signers (for example `...\AppData\Local\Microsoft\Teams\Update.exe`),
- keep `Users\Public` and `Temp` with no exceptions, because legitimate software almost never starts from there.
